# AgentMesh 交接要点：验收门推进、省用边界与仓库现状

> 来源：工作区 `D:\ZISHIKU\AI\AgentMesh` 的 `AgentMesh.md`（PRD 4.1，748 行 / 46,543 bytes）。关联文档：`d373d32b-0b73-4671-8066-ccf944a194b2`（一期设计定稿）、`0358ccfe-7114-4e6d-9fbf-9e52ca0515d2`（PRD 2.0 收敛）。本文只记交接所需的计划结构、省用边界与仓库现状，不复制 PRD 正文。

## 1. 交付按验收门推进，不按日期倒排（D18）

- 五道门：Gate-0 能跑 → Gate-1 能派活 → Gate-2 能看进度 → Gate-3 能重来 → Gate-4 能交付；未过门不进下一阶段（对策：防"抢跑"导致返工与演示翻车）。
- 六条业务门槛与门对应：能派活、能看到进度、能重来、不被卡住、出事能看清、不用维护。
- 三档发布口径：可用预览（Gate-0/1）、试用版（Gate-0~3）、演示版（Gate-0~4 全过，才允许对外说"比单干强"）。
- 里程碑 M1-M10：M1 Herdr 连通、M2 适配器打通、M3 消息闭环 → M4 小组与子代理 → M5 派活入口 → M6 看板 → M7 失败重来 → M8 待我处理 → M9 省用 → M10 运维与自愈。M8-M10 在 M7 之后，不提前铺开。

## 2. 编号体系与已修过的一致性问题（D23）

- 规模：FR 14 组共 94 条；A 基础验收 12、F 功能验收 17、NF 非功能验收 4、Gate 5、M 10、US 14、D 23；编号互不重叠。
- 已修正两处硬伤：页眉"108 条需求"与实际 94 条不符（改 94、记 4.1）；目标 G1~G7 与验收门 G0~G4 撞号（目标改 G-1~G-7、成功标准改 SM-1~SM-7、验收门改称 Gate-0~Gate-4）。
- 后续改 PRD 必须保持这套编号不撞车，且每项 FR 需在里程碑与验收章节都有归属。

## 3. "省用"的硬边界（D20、FR-13.9~13.11、F16）

- 只减"重复搬运"：同一任务链内同一内容只搬一次（按引用传文件路径 / 产物编号）、通知与看板只送摘要、失败重来只重发失败那一步。
- 三条禁止：不得降可读性（摘要可一键展开原文）、不得增人工动作（去重与引用自动完成）、不得打断任务（超限只提示一次）。
- AgentMesh 自身不调用模型；省的是 Agent 往返与上下文重复，不是砍功能、截断上下文。

## 4. "比手动更省事"的正面口径（2.4、D21、F17）

- 2.4 逐条对比"单个应用 + 手动维护"，并明确承认：**单任务单 Agent 时手动更快，不强推**——避免为用而用。
- 用户只做两件事：派活、看结果；路由、编号、去重、重连、对账全部由系统完成。

## 5. 仓库现状（交接基线）

- 只有一份 PRD（`AgentMesh.md`，4.1）+ 静态 UI 原型（`ui/index.html`、`ui/styles.css`、`ui/app.js`），数据全为 mock。
- 尚无：Core 后端、真实消息路由、SQLite、Herdr socket 接入、MCP/WS 适配器、package.json、git 仓库——不要假设是 npm 工程。
- UI 已过 `node --check`，用无头 Edge 截图 + CDP 实际点击验证；preview 图只代表界面，不代表功能打通。
- UI 尚缺派活输入框与任务看板，是下一步核心。

## 6. 接手顺序与证据要求

- 先读 PRD 再读 UI；按 M1→M2→M3 打通真实收发闭环，再 M4→M7；Gate-0 未过不做 UI 美化。
- 每个里程碑交证据（命令输出、截图、真实交互）；mock 不得说成打通，真实环境缺失时明确标"骨架 + mock"。
- 发现 PRD 与实现冲突，先记录冲突并问用户，不默默改目标。
