# AgentMesh 会话优先信息架构（session-first）与会话成员持久化缺口

> 工作区 `D:\ZISHIKU\AI\AgentMesh`。2026-10-30 同一会话的第四阶段：在已完成「原型接后端」之后，按用户截图与要求把 `/` 的信息架构改为「会话为主体」。前置阶段的路由契约、异常矩阵、桥接映射见文档 `657ebab7-c6e8-46eb-a5e8-72c38c2890a0`；范围收敛与「改原型本体、不做桥接副本」的由来见 `672f0d19-ab57-44fc-892f-4224d5dfb5b9`。本文只记录本阶段新增的 IA 决策、实现位置与未闭合的后端契约。

## 1. 用户给定的 IA 规则

- 左侧列表是**会话**，不再按项目/状态分组；会话是主体。
- 每个会话下应展示**参与当前会话的智能体与应用**（成员 chips/头像）。
- 会话中必须能**添加智能体和应用**，且「新建会话」「添加成员」都要有明确入口，不能只有一个不显眼的 `+`。
- 任务的可视化与交互保持原型既有模式（任务线、交接、泳道、画布），不另起一套视觉。

## 2. 已实现（提交 `4abd509`）

| 位置 | 行为 |
|---|---|
| 左侧列表 | 统一「会话」分组，每项显示标题、路径、状态、参与成员头像 |
| 搜索框下 | 新增「+ 新建会话」，弹窗填名称并多选 Agent/应用 |
| 会话头 | 显示当前会话全部参与者 chips |
| 会话头「+ 成员」 | 打开成员选择器，可加入智能体或应用 |
| 任务可视化 | 沿用原型的任务线/交接/泳道/画布，未改模式 |

- 内置可选成员 14 项：GPT、Claude、Grok、Gemini、豆包、Kimi、DeepSeek、Qwen、Sol、Opus、Codex，以及 VSCode、Figma、浏览器。
- 改动文件：`prototype/AgentMesh-原型.html`、`prototype/prototype-bridge.js`，并同步 `docs/frontend/agentmesh-frontend-contract.md`。

## 3. 边界与未闭合项（不得假装已持久化）

- 会话成员选择目前是**前端本地状态**：界面可加、可看、可切换，但刷新后不保留。
- 后端尚无「会话成员表」；「新建会话」只能复用现有任务创建能力，多成员会话无法落库。
- 最小补齐方案：新增 `session` 成员关系模型（会话 ID + 成员 ID + 角色），前端再补保存动作；在此之前成员只停留在界面层。
- 上阶段遗留的未接入项依旧有效：接入成员/模板向导、通知、任务看板完整操作（取消/归档/重开）、自定义通信线与通信流、系统状态/诊断、嵌入式终端、消息撤回/重试。

## 4. 验证证据

- 浏览器实测：左侧分组为「会话」、1 个会话、1 个成员头像、会话头 1 个 chip；「添加成员」弹窗 14 个选项，添加后 chips = 2；「新建会话」弹窗含名称输入与 15 个成员选项；控制台无报错。

## 5. 交付教训

- 用户说「没看到改动」时，若改动只在 404/5xx/网络错误分支（如路由守卫），正常浏览确实不可见；应同时给出首屏可见变化，并说明生效条件，不能把错误兜底算作页面改动。
- 本阶段起，`/` 的主线是「会话 → 参与者 → 任务可视化」，后续补功能入口应挂在这一结构下，而不是恢复项目/状态分组。
