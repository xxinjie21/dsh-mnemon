# 豆包第二批补词实测 + 全字段补词性价比排序

## 背景与执行闭环
用户转交豆包第二批补词（变更清单写在 `docs/前端改造计划.md`「症状词典补词第二批」小节，明细另存工作区 batch2 目录的 change_report.json + 三片 result 文件）。执行前先核实：**落库真正读的是 `java-backend/src/main/resources/dictionaries/symptoms.json`，豆包报告的清单文件不参与落库** —— 必须确认 JSON 本体真被改动，否则重启白跑。

本轮闭环（顺序固定）：
1. 核实源码 `symptoms.json` 标准词数 = 647（573 → 647，+74，与豆包"74 新增"对上），且已提交、`target/classes` 同步为 647。
2. 查 ES `term_symptom` 计数发现仍是 **573**（旧批）→ 证明「词典文件改了但 ES 未重建」是可观测状态。
3. 重启 java-backend 触发词典重播：启动日志出现 `[ES] 索引 term_symptom 重建完成，术语数: 647` 与 `[词典] symptom (org='') 重建索引，647 条，版本 4b2023b9...` → ES 确为 647。
4. 清 Redis 报告缓存 `tcm:ehr:cache:stats:report:*`（本轮清掉 5 键）后再取数。
5. 提交「仅归一」任务（`normalize-only`，全库 34182 条），终态 COMPLETED success=34061 / failed=93（93 条永久失败 = 尚无结构化数据，与基线一致）。
6. 取真实数据反馈给豆包，作为第三批校准依据。

## 关键发现：补词的前两批清单生成口径
- 候选清单来源 `docs/症状补词候选-第二批给豆包.csv`（3790 词，按「覆盖 ≥5 次」筛选）；旧版 `症状补词候选-高频2000.csv`、`症状补词候选-修正版高频3000.csv` **口径有误，废弃不用**。
- 清单原本**不标记哪些词已处理**，易导致重复劳动。第三批改为**重新生成**：用当前词典（标准词 + 别名，实测 3453 条）剔除已收录词，再剔明显噪声，导出 top3000 → `docs/症状补词候选-第三批给豆包.csv`（覆盖 75868 条未归一症状）。

## 第三批候选池降质（如实判断）
生成的 top3000 里噪声仍多：病程/诱因描述（活动后缓解、休息后缓解、遇劳加重、受凉后、持续性发作）、属性词（黄褐色、泡沫多、成形偏干）、脉象残留（左不受按、外侧分支略沉）、饮食控制类（控制饮食、清淡饮食）、否定式（不痛不痒、按之不痛）、口语残片（心里烦得、食量一）。规则过滤已证明筛不干净，须靠医学判断兜住；真正该补的是「部位 + 症状」复合发现（脐右压痛、咽后壁淋巴滤泡、咽喉干），延续现有词典惯例（113/535 标准词含部位）。
高收益词接近补完 → 后续批次边际收益将递减；「某批找不到多少该补的」本身是有效信号，应转投其他字段。

## 可复用经验
- 词典变更生效链是**三段**：源码 JSON → `target/classes` → **重启后端触发 ES 重建**。只改文件不重启，ES 仍是旧计数（本轮实测 ES=573 vs 文件=647）；核验手段 = ES 计数 + 启动日志的「重建完成，术语数: N」。
- 变更清单/报告文件 ≠ 落库文件。收到外部（豆包）报告时先确认被系统真正读取的那个文件已变。
- 量测归一率前必须清 Redis 报告缓存，否则读到 30 分钟内的旧报告。
- Git 侧 CRLF→LF 警告（EntityNormalizer.java、NlpBatchServiceImpl.java、docs/质控提升计划-归一率与抽取正确率.md）无害，不影响提交。
