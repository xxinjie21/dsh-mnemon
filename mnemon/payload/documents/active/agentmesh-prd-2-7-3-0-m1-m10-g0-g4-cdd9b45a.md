## 2. 架构参考：别人为什么这么做（第 2.3 节）

| 参考 | 架构事实 | 对 AgentMesh 的启示 |
|---|---|---|
| multica | 客户端 → Go 服务 ← PostgreSQL；守护进程通过 WebSocket 领任务，再调本机 AI 工具；PostgreSQL 是唯一事实源，Redis 可选 | 服务端只做事实源与调度；执行永远在本机；单机可省 Redis，用进程内实现 |
| Herdr | 单二进制 Rust 进程，自管 PTY / pane / 终端；对外暴露 socket API 与 CLI 供 Agent 反控 | 让 Agent 能"反控工作台"（派活、等结果），而不是只被人操作 |
| DeepSeek Harness | 一切皆插件；会话是 append-only 事件流，Resume / Fork / Replay 都作用在同一条流上 | 记录写成只追加消息流；复盘、重试、接手都从这条流读，不另造状态 |
| Claude Code / Gemini CLI | 子代理有深度上限与超时；跨进程通信走工具协议（MCP），不解析终端文本 | 子代理限层数与超时；消息只走适配器，绝不抓屏解析 |
| n8n | 执行列表可按状态过滤、失败可单独重跑 | 看板与失败重来照此形态做 |

### 2.1 由此确定的五条架构原则

1. **一个事实源**：SQLite 是唯一真相，看板、通知、摘要都从它派生。
2. **只追加**：消息、任务、通知都是事件流；改动用新记录表达，旧记录不改。
3. **本机执行**：AgentMesh 不替 Agent 干活，只路由与记录。
4. **适配器说话**：跨进程只走 MCP / WS 结构化消息，绝不解析终端输出。
5. **让 Agent 反控**：Agent 能通过工具派活、提问、等结果。

## 3. 架构边界（第 5.2 节，六条硬约束）

| 边界 | 约束 |
|---|---|
| Core ↔ Herdr | 只通过 socket API / CLI；不 fork、不改 PTY 代码 |
| Core ↔ CLI Agent | 只通过 MCP 适配器；不抓终端输出 |
| Core ↔ GUI 应用 | 只通过 WS 适配器；不启动进程、不嵌窗口 |
| 事实源 | 只有 SQLite；看板 / 通知 / 摘要全部派生，不做第二份状态 |
| 执行位置 | 永远在 Agent 自己的进程里；Core 不执行命令、不调模型 |
| 失败边界 | Herdr 挂了不影响 GUI 与总线；Core 挂了不影响 Herdr 终端 |

## 4. 依据架构原则补齐的需求

- **FR-1.6**：节点标明接入程度——已接入（可收发）/ 已托管（只能用）/ 已连接（只读了 GUI），能力不夸大（对应决策 D17）。
- **FR-8.5**：统一 MCP 工具契约（派活 / 提问 / 等回复 / 回复 / 收件 / 确认 / 查状态），每个工具都有超时与可读错误返回；WS 帧与之一一对应。
- **FR-8.6**：断线重连续投。
- **FR-14 运行与运维**：健康面板（Core / Herdr 连接 / 数据库 / 适配器会话，三秒内可判断）、一键导出诊断包（不含密钥）、恢复动作提示、事实源一致性（重启后看板/通知/摘要一致）。
- 目标映射（0.1）增补"Agent 能反控"与"出事能看清"两行，全部 14 组需求必须落在映射表内，表外能力一律不做。

## 5. 计划结构（第 11 章）

### 5.1 三阶段 / 十里程碑 M1–M10

| 阶段 | 里程碑 | 产出 | 验收门 |
|---|---|---|---|
| P0 打通 | M1 Herdr 连通 | Core 能启动 pane、读终端、拿到 Agent 状态 | G0 |
| P0 打通 | M2 适配器打通 | MCP 与 WS 各跑通一个真实节点 | G0 |
| P0 打通 | M3 消息闭环 | 发送 / 提问 / 回复 / 超时在真实节点跑通 | G1 |
| P1 能用 | M4 小组与子代理 | 建组、组播、派生子代理、级联销毁 | G1 |
| P1 能用 | M5 派活 | 一句话派给成员或小组，10 秒内可撤回 | G2 |
| P1 能用 | M6 看板与交接 | 看状态、看进展、看摘要、点回原文 | G2 |
| P1 能用 | M7 失败重来 | 失败高亮，一键只重跑失败那一步 | G3 |
| P2 好用 | M8 待我处理 | 只收需要人动手的事，可设提醒偏好 | G3 |
| P2 好用 | M9 省用 | 引用传递、只送摘要、链内去重 | G4 |
| P2 好用 | M10 运维 | 健康面板、诊断包、恢复提示 | G4 |

### 5.2 五道验收门（每道门全部通过才进入下一阶段）

| 门 | 门槛 | 对应验收 |
|---|---|---|
| G0 能跑 | 真实节点连上，能收发一条消息并查到记录 | A1、A2、A8、F12 |
| G1 能派活 | 一句话派给成员或小组、可撤回、互不串台 | F1、F2、F3、F7、A3、A4 |
| G2 能看进度 | 看板显示负责人 / 进展 / 卡点 / 接手指南 | F4、F5、F8、F11、A6、A7 |
| G3 能重来 | 失败可见，一键只重跑失败步，卡住会提醒 | F6、F9、F10、F13、A9 |
| G4 能交付 | 省用生效、健康可判、诊断可导出、重启不丢 | F14、A10、A11、A12 |

依赖链：`M1 Herdr → M2 适配器 → M3 消息闭环 → {M4 小组/子代理 | M5 派活 → M6 看板 → M7 失败重来 | M8 待我处理 → M9 省用 → M10 运维}`。原则：M1–M3 不跑通，后面全是演示；M5–M7 是"比单干强"的核心闭环，优先于 M8–M10。

### 5.3 优先级、周期与发布口径

- 优先级：P0 = 缺了"派活 → 看进度 → 能重来"就断；P1 = 缺了用户会返工或反复问；第二波只记名字（再次派活、搜索、按目录分组），不进本期。
- 资源假设：1–2 人全栈 + 已有 UI 原型；相对投入 P0:P1:P2 ≈ 3:5:2，具体日期按人力再定（不按日期倒排，D18）。
- 变更纪律：新增需求必须先落进 0.1 目标映射表，否则进第二波。
- 发布口径（D19）：可用预览（内部 / 自测）= G0、G1；试用版（5–10 位真实用户）= G0–G3；演示版 = G0–G4。

## 7. 计划类风险（第 12 章新增）

| 风险 | 影响 | 应对 |
|---|---|---|
| 适配器协议各自为政 | 接入成本高 | 统一 MCP 工具契约（FR-8.5），WS 帧一一对应 |
| 看板与事实源不一致 | 状态失真 | 看板只读派生自 SQLite（D16） |
| 跳过验收门抢跑 | 演示不可信 | 未过门不进下一阶段（11.5 顺序纪律） |
| 人力不足 | 周期拉长 | 按相对投入比排期，先保 M5–M7 核心闭环 |
