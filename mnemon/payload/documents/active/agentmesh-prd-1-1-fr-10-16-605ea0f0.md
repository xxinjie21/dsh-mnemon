# AgentMesh PRD 1.1 功能补强层

> 来源：工作区 D:\ZISHIKU\AI\AgentMesh 的 `AgentMesh.md`（PRD 部分，补强后 771 行 / 43,620 bytes）。配套的一期设计定稿见文档 d373d32b-0b73-4671-8066-ccf944a194b2。本记录只保留 1.1 补强的可复用结论与理由，不复制全文。

## 1. 补强起因（用户主导的判断）

- 用户先问"要达到商业应用还需要补什么"，随即纠正优先级：**先把功能补齐，不要让用户觉得它解决不了实际问题、还不如单一应用通讯**；商业能力（安装、计费、合规）排序不应排在功能前面。
- 由此确定唯一价值判断口径：**它能不能完成单独用一个 Agent / 应用做不到的事**。本轮只做"与单干对比"，不做规模扩张论证。

## 2. 与单干逐项对比结论（PRD 1.5 / 3.4）

| 能力 | 单干时怎么办 | AgentMesh 做法 | 承接需求 |
|---|---|---|---|
| 派活 | 自己开窗口写指令 | 界面一句话派给指定成员 / 小组 | FR-10 |
| 追踪 | 翻终端日志 | 任务看板：谁在做、卡在哪、下一步 | FR-11 |
| 上下文 | 复制粘贴 | 组内共享任务历史与产物 | FR-12 |
| 复核 | 自己回忆 | 产物/命令可点开、失败可重来 | FR-13 / FR-15 |
| 复用 | 每次重搭 | 模板配方保存、导入导出 | FR-16 |

判定口径写入 PRD：**任一项做不到，就不对外说"比单干强"**。

## 3. 能力清单（M1~M10）与三波顺序

第一波（产品能否立住的关键闭环）：**M1 真实消息收发闭环（MCP/WS 适配器真正连上 Core，取代 mock）→ M2 界面派活 → M3 任务看板 → M6 失败可视化与一键重来 → M7 模板即配方**，串成"能派活 → 看到进度 → 能重来 → 能复用"。
第二波（拉开与单干的差距）：M4 共享上下文、M5 产物可点开、M8 接入更多真实 Agent。
第三波（体验升级）：M9 GUI 窗口镜像嵌入、M10 不打断的节奏。

## 4. PRD 1.1 新增内容结构

- 新增 1.5 节（比单独用一个 Agent 强在哪）、3.4 节（价值判断表）、3.1 G7 / 3.2 NG7 / 3.3 M7（第一波闭环成功标准）、2.1 第 4 条痛点（上下文与产物散落）。
- 新增 7.10~7.16 功能需求：FR-10 派活入口、FR-11 任务看板、FR-12 共享上下文、FR-13 产物与失败处理、FR-14 资源与并发边界（同时运行节点上限、单条消息 1 MB 上限等）、FR-15 撤回与取消、FR-16 配置与模板导入导出；FR-6 增补 FR-6.7 派活入口、FR-6.8 任务看板标签。

- 新增 11.2 功能补强验收 F1~F10、11.3 发布门槛；12 章改为单期三波并标注原型已具备/待补。

## 5. 关键设计决策（D9~D13）

| 编号 | 决策 | 结论与理由 |
|---|---|---|
| D9 | 派活入口 | 界面输入一句话即可派活；不做流程编排 |
| D10 | 任务看板 | 看板只读派生自任务与消息表，不引入第二套状态，避免状态失真 |
| D11 | 共享上下文 | 只读共享，不改写各 Agent 原生会话 |
| D12 | 失败重来 | 只重发消息、不重跑 Agent；旁支保留，与 FR-5 消息级重试口径一致 |
| D13 | 商业能力 | 暂不进 PRD 主线，功能闭环通过后另起文档 |

## 6. 发布门槛（11.3）

第一波必须同时满足才允许对外演示"比单干强"：能派活（F1、F2、F3、A8）/ 能看到进度（F4、F5、A6、A7）/ 能重来（F6、A9）/ 能复用（F8、F9、F10）。

## 7. 原型缺口（待实现）

原型已具备消息、模板、派生子代理交互；**缺派活输入框（FR-10）与任务看板标签（FR-11）**，这两项是第一波核心，下一步建议直接落到原型。

## 8. 协议层调研结论（附录 B.2.1）

本期不引入外部协议依赖，保持本地轻量；但消息模型（任务、状态、事件）与 A2A（已捐给 Linux Foundation / Agentic AI Foundation）、AG-UI 的概念对齐，A2A 作为将来跨机/跨产品通信的二期候选，以降低迁移成本。
