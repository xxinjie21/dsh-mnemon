# tcm-ehr-qc 方法内注释编号整改（规范 6）落地记录与执行口径

## 背景与结论

用户明确要求：**项目里所有方法内注释都必须按方法内部流程编号**，使用 `// 1.` `// 2.` `// 3.` 形式，必须这样写，无一例外。本轮据此对 `tcm-ehr-qc` 的 `java-backend` 做全库整改。

最终指标：

| 指标 | 数值 |
|---|---|
| 含方法内注释的方法 | 372 |
| 方法内注释段总数 | 1087 |
| 已编号段 | 1053 |
| 未编号段 | 34（**全部是合规的层级子编号**，如 `1.1` / `2.1` / `3.5` / `25.8`）|

编译验证：`mvn clean test` **637 通过**（与既有回归基线一致）。

## 编号规则（可执行口径）

```
// 1. 第一步做什么
//    续行说明（保持缩进，不编号）
//    ...
// 2. 第二步做什么
// 3. ...
```

- **一段连续 `//` 注释 = 一个编号单元**，不是一行一个编号。多行注释的续行**不编号**，仅保持对齐缩进。
- 主流程用 `1.` `2.` `3.`；主步骤下的子步骤用层级编号 `3.1` `3.2`，`0.5` 这类前插步骤也允许；版本号型前缀（如 `// 26.10：`）同样是合法形态，不得改动。
- 检测/统计脚本也须按「注释段」而非「注释行」计数，否则会把续行误报为未编号。

## 统计口径的两次纠错（重要教训）

1. 首版统计报「1255 条注释」，按行计数，实际按段只有 1087 段。
2. 首版试点脚本给**多行注释的每个续行都编号**（同一段变成 1、2 两个编号），破坏可读性 —— 已还原并改为「一段一号」。
3. 检测脚本最初把续行算作独立未编号条目，产生 `saveFor 3/7` 之类假告警；按段重算后真实未编号从 186 个方法降至 39 段，其中 34 段是合规子编号。

## 自动化批改踩的坑（必须避免重演）

全库批量改注释的风险远高于预期。脚本两类误判共破坏 **15 处**代码，造成短暂编译失败：

| 误判 | 后果 | 修复方式 |
|---|---|---|
| 把 `// 26.10：告警先累积…`（**版本号**）当作步骤编号，剥掉 `// 26.` 前缀 | 注释行变成裸文本 `10：告警…`，编译报非法字符 | 恢复原文 `// 26.10：` |
| 多行注释**续行**被单独编号/剥壳（`LEAD_NUM_RE` 在已含编号的块里误剥 `//`） | 续行丢 `//` 变成裸文本，编译失败 | 恢复 `//` 并重编号 |

涉及文件：`LlmConfigStore`、`QcRuleStore`、`EntityNormalizer`、`GovernanceServiceImpl`、`JwtUtil`、`QcRuleDescriber`、`LlmClient`、`DictionaryServiceImpl`、`LlmConfigServiceImpl`、`OrgServiceImpl`、`QcServiceImpl`。

排查中的额外陷阱：

- 扫描时把代码/字符串里的 `//`（URL 等）当成注释；Java 文本块（`"""`）内的中文提示词行也会被误报为「被剥掉 `//`」，需按文件头 `"""` 出现次数奇偶判断是否在文本块内。
- 修复用的正则不能依赖行内容字符集（行内含全角 `（）`、`——` 时匹配失败），改用编译错误输出行号精确定位再修。
- 判断「被剥壳」的行要结合前后上下文：先看该行是否紧邻已有编号的注释段。

**做法建议**：先用单个文件试点（本轮试点 `LlmConfigStore.java`）看输出，再逐步扩大；不要一次全库跑。每批都必须跑 `mvn clean test` 再提交。
