# 标准化报告缺陷排查：可归一率恒 100%、口径混用、降级方案取舍

承接既有文档 `2c4d269c-9de4-4a61-b5c0-11e73f144450`（该文记录 normalizable ≈ 99.98%、界面不引用它，并把它解释为「算法口径」）。本轮进一步证明它不是「口径不同」而是**逻辑恒定**：分子必然等于分母，指标零信息量。该旧文档的结论「测的是匹配算法有没有 bug」应以此为更新。

## 结论一：词表改动只需重跑归一，不需要重跑解析（指令链事实）

解析只负责把文本抽成实体，「实体 → 标准词」的映射由归一完成。补词表后的正确生效链路是：**改词表 → 重启/导入触发 → 重建 ES → 重跑一次「仅归一」**。

- 已验证存在且早有注释说明用途、却从未被调用的 API：`submitNlpNormalizeBatch` → `POST /nlp/extract/batch/normalize-only`（`frontend/src/api/nlp.js:46`，注释「补词典后让新词生效」）。
- 错误指引曾扩散到 4 个页面（报告页、明细组件、词典导入页、提案审核页），其中词典导入页不只是文案错，**按钮实际调用了重抽 `submitNlpBatch`**（`frontend/src/views/DictionaryImport.vue`），属实现错误。已改调 `submitNlpNormalizeBatch`。
- 影响量级：按旧提示重跑解析约 1 小时，正确做法约 17 分钟。
- 修正已随 commit `5ea6b77`（"修正「标准化质量报告」及相邻页面的 8 处描述/逻辑错误"）提交，`vite build` 通过。

## 结论二：normalizableRate 恒 100% 是逻辑缺陷，不是口径问题

`StandardizationReportService#normalizableRate`（约 860-884 行）三条判据的语义是 `defect = isMisrouted || containsAny(PHYSICAL_SIGN) || content.length() <= FRAGMENT_MAX_LEN`（`FRAGMENT_MAX_LEN = 2`，`PHYSICAL_SIGN = {压痛,触痛,叩痛,反跳痛}`），随后：

```java
if (defect || !isInDict(content, symptomDict)) continue; // 不在词典 → 出局
r.setDenominator(+1);                                    // 只有「在词典里」的进分母
if (m.get("normLevel") != null) r.setNumerator(+1);       // 在词典里 ⇒ normLevel 必然非空
```

**「在词典里」与「已归一」是同一件事**，因此分子恒等于分母 → 报告里出现 `{"denominator": 40165, "numerator": 40165}`。实测复核（合格病历症状实体）：总数 185580，normLevel 非空 101475，为空 84105 —— 证实分母只吃已归一那批。

**判别规则（可复用）**：看到比率恒为 100%，先查分子分母的筛选谓词是否同义；「先过滤再计数」的写法极易把条件写进分母而非只写进分子。同时，`coverage` 才是唯一有意义的归一率（症状字段实测 54.7%）。

## 结论三：score/qc 用全量、dataset 用合格病历 —— 口径混用

`computeReport`（约 356-357 行）传 `rows` 给 `scoreDistribution` 与 `qcCoverage`，却传 `qualified` 给 `datasetShape`；于是 `score.total = 34154` 与 `dataset.recordCount = 28801` 并列显示，用户以为分母相同。

决策：**保持分数用全量（语义正确）**。待复核（60-79 分）与无效（<60 分）共约 5361 条若被排除，分数分布会恒定挤在 80-100，「评分区分度不足」的告警随之失效 —— 这正是「用调口径掩盖问题」。修法是**改标签不改数据**：每个数字旁标明「全部病历」或「合格病历」，并说明差异原因。

## 结论四：降级方案的取舍 —— 不用不可靠判据做主观排除

曾计划把 normalizable 的分母改为「全部症状实体 − 三类噪声」。实测否定了这个方案：

| 项 | 数值 |
|---|---|
| 症状实体（合格病历） | 185580 |
| 已归一 | 101475 |
| frag（len ≤ 2） | 67892（36.6%） |
| phys | 388 |
| misrouted | 34 |

`len <= 2 = 碎片` 把**两字真症状**（如「纳差」「多梦」）一并判为噪声，噪声高达 36.6%，新分母得到的可归一率 34.2% **反而低于 coverage 的 54.7%** —— 用坏判据修分母，会把真症状排除出去，是比原缺陷更隐蔽的错误。

**采纳的结论（诚实口径）**：不预先判断哪些「不该算」，只如实分类构成。

```
症状实体 185580
├─ 已归一      101475 (54.7%)
└─ 未归一       84105
   ├─ 词表未收录  77135  ← 补词表可解决（dictionaryGap）
   └─ 抽取问题    6542   ← 修抽取可解决（fragment / misrouted / inferred 等）
```

即：保留 `coverage` 作为唯一归一率指标，强化既有 `unmatched` 构成分析（dictionaryGap / fragment / misrouted / physicalSign / inferred），废弃或停止展示 `normalizable`。**核心原则：不让「抽取问题」伪装成「词表问题」，两个数字分开说，谁的问题谁背。**

## 结论五：byMonth 小样本会误导

`byMonth`（约 499 行起）按 `visitTime` 的 `YearMonth` 分组，无 `visitTime` 归入「未知」组不静默丢弃；组内症状率 = `symHit / symTotal`。问题不在算法：`2025-12` 仅 5 条病历却显示 `symptomRate = 92.6%`，与全库 54.7% 差距悬殊，图表上会被读成「某些月做得很好」。修法：记录数低于阈值（如 10）的月份加「样本少」标注。

## 排查经验（可复用）

- 用户一句「检查要完全」往往意味着上一轮只扫了文案没扫数据链路：**体检报告页要逐字段追数据来源与分母，而不是只读提示文字**。
- 先写脚本从库/接口取实测数字，再改代码；本轮每个修法都由实测数据支持或否定（尤其结论四，是数据推翻了原方案）。跑统计脚本时注意脚本名冲突会静默输出旧内容 —— 出现可疑「旧结果」时重跑并核对脚本。
- 当修复方案依赖某个判据时，**先量化该判据的触发比例**：占比过大（如 36.6%）通常说明判据本身错了，而不是数据脏。
