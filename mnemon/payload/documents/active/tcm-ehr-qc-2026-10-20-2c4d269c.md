# 标准化质量报告「归一率」口径与图表视觉误读排查

## 背景
「仅归一」批跑后（见文档 `5440bc2e-50ab-4420-906c-bd897d9dfdc5`），用户质疑：标准化质量报告里为什么很多实体的归一率显示 100%。本排查确认后端数据与前端渲染都无 100%，问题出在图表可读性。

## 结论一：报告里有两个同名不同义的「归一率」，只有一个出现在界面上

### coverage 各字段归一率（页面实际使用的那个）
- 分母 = 该字段**全部已抽取实体**；分子 = 其中已归一的条数，逐条实体计数。
- 后端：`StandardizationReportService#coverage`（约 670-704 行）建表只列「有词典」的类型（`if (!t.dict()) continue`），`countEntities`（约 707 行起）逐实体累加 total/normalized。
- 同一处还打标 `suspectedStaleExtraction = termCount>0 && total>0 && normalized==0`，用于区分「解析早于词表建立」与真正的词表缺口。
- 当前实测（34154 完成分母）：症状 198030/78763 = 39.8%、证候 62.1%、病因 30862/19286 = 62.5%、方剂 71.6%、舌象 78.4%、疾病 82.7%、脉象 91.7%、中药 98.6%、治法 2/5 = 40.0%（样本极小）。

### normalizable 可归一实体归一率（API 有，界面不用）
- 数字：denominator 27981 / numerator 27976 = **99.98%**；VO 字段带「乙类 / 可归一实体归一率」注释。
- 分母**刻意缩小**为「已抽取 + 非抽取缺陷 + 已在症状词表内」：词表里没有的标准词属词表缺口本身，计入分母会抹掉「补词表能改善多少」的信号。因此它恒接近 100%，测的是「匹配算法有没有 bug」，不是整体归一率。
- 前端主页面**完全没有引用**它：`StandardizationReport.vue` 注释明说技术口径（甲类/乙类、normLevel、可归一实体）只在文件内部使用、不出现在界面上；`StandardizationDetails` 亦然。它仍留在 API 响应里，是未来调用方（CSV 导出、第三方）误读的隐患。

**判别规则**：报告里任何一个「归一率」必须问清分母 —— 全部实体（业务口径，当前 39.8%）还是仅词表内实体（算法口径，99.98%）。

## 结论二：图表不存在 100%，「显示 100%」是视觉误读
- 用户所指位置：`StandardizationCharts.vue` 图一「各类术语归一率」，注释即「条长 = 归一率（0~100%），越短越该先补」。
- 数据：`covBars`（约 118-130 行）过滤 `total>0` 后 `rate = normalized/total`，按 rate **升序**排序（最差在最上）；渲染时 `data: rows.map(r => Math.round(r.rate*100))`，max 100。故柱子只可能因 `normalized == total` 才满格，实测满格集合为空。
- KPI 卡「术语归一率」用症状字段（`symRate` = normalized/total）→ 39.8%；明细组件已删除归一率展示；CSV 导出不含可归一率；`StructuredDataCard` 无百分比渲染。
- 误读成因：9 根柱里有 5 根 >70%（方剂 71.6、舌象 78.4、疾病 82.7、脉象 91.7、中药 98.6），在 0~100 坐标系里 90%+ 与满格肉眼难分；同时长条视觉压制真正短板（症状 39.8%，未归一约 11.9 万条，是中药 6164 条的 19 倍）。
- 结论：不是数据错误，是**符号化不足** —— 无数值标注、无参考线、只给比率不给绝对量，导致「越短越该先补」的图意失效。

## 候选改法（等待用户拍板，未实施）
- (a) 柱尾直接标注百分比，消除满格歧义。
- (b) 加 90% 参考线/及格线。
- (c) 并列显示未归一绝对条数（中药 6164 vs 症状 119267），让「先补谁」一眼可见 —— 与图表标题语义最贴合。
- 助手倾向 (a)+(c)。

## 排查经验（可复用）
- 面对「页面显示的数字不对」：先在**后端统计口径**与 SQL 直查之间对账，再逐层查前端渲染路径（KPI 卡 → 图表组件 → 明细组件 → 导出），不要在未确认展示位置前改代码。
- 排查时曾误判「前端 167 行注释说不用 ≠ 某组件仍在展示」，实际逐文件 grep 后确认界面确无该指标；**以 grep 结果为准，不以猜测的组件归属为准。**
- 前端注释里点名的历史 bug（如按 field 建 Map 又按 label 查导致恒 0）说明 label/field 不同名是此类页面的通病，改动对齐逻辑时须核对。
